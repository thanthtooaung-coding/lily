You are a senior Python backend engineer and system architect.

I am building a hackathon project called:

# Lily
AI-Powered Incident Response & Automation Platform

The goal of Lily is to receive incidents/events from users or external systems, analyze them using AI, automatically trigger workflows through n8n, notify the appropriate people, optionally request human approval, execute actions through Lily's FastAPI backend, and keep a complete incident history.

==================================================
1. CORE CONCEPT
==================================================

Lily follows this flow:

User/System
    ↓
Lily FastAPI Backend
    ↓
Create Incident
    ↓
n8n Automation
    ↓
AI Analysis
    ↓
Severity / Priority / Recommended Action
    ↓
Notification
    ↓
Optional Human Approval
    ↓
Execute Action through Lily API
    ↓
Update Incident
    ↓
Store Audit Log
    ↓
Dashboard / Reporting

Example:

A monitoring system reports:

"Production payment API response time increased by 300%."

Lily receives the incident.

Lily creates:

{
  "severity": "HIGH",
  "service": "payment-api",
  "title": "Payment API latency increased",
  "description": "Production API response time increased by 300%"
}

n8n receives the incident.

n8n sends the incident to an AI model.

AI determines:

- severity
- category
- impact
- urgency
- recommended action
- whether human approval is required

n8n then sends a Telegram notification.

Example:

🚨 Lily Incident Alert

Service: payment-api
Severity: HIGH

Payment API latency increased by 300%.

Recommended action:
Restart payment-api and monitor response time.

Human approval required: YES

The user can approve/reject.

If approved, n8n calls Lily's FastAPI endpoint to execute the action.

Lily records everything in the database.

6. INCIDENT ANALYSIS
==================================================

Create:

POST /api/v1/incidents/{incident_id}/analyze

This endpoint should:

1. Load the incident.
2. Prepare an AI analysis request.
3. Return structured analysis.
4. Save the analysis to the incident.
5. Update severity/category/etc.
6. Determine whether approval is required.

Example response:

{
  "incident_id": "uuid",
  "severity": "HIGH",
  "category": "PERFORMANCE",
  "impact": "Users may experience slow payment processing.",
  "urgency": "HIGH",
  "recommended_action": "Restart payment-api and monitor latency.",
  "requires_approval": true,
  "reason": "Restarting a production service can affect active users."
}

The AI response MUST be structured JSON.

Do not rely on parsing arbitrary natural language.

n8n is a CORE part of Lily.

Do not put all automation logic inside FastAPI.

- database
- incidents
- actions

It should accept:

    "requires_approval": true
  }
}

29. IMPORTANT DESIGN PRINCIPLES
==================================================

Follow these principles:

1. Keep FastAPI responsible for core business logic.

2. Keep n8n responsible for orchestration and automation.

3. Do not tightly couple FastAPI to n8n.

4. Do not tightly couple the backend to Telegram.

5. Use service abstractions.

6. Use dependency injection.

7. Use environment variables.

8. Never hard-code secrets.

9. Use UUIDs.

10. Use database transactions.

11. Validate all request data.

12. Return consistent API responses.

13. Keep the implementation hackathon-friendly.

14. Avoid unnecessary microservices.

15. Do not implement dangerous real server commands.

16. Make remediation actions simulated but architected for real integrations later.
